# 2026-09-22：原生窗口缩放期间延后 WebGL 重建

用户进一步确认：卡顿发生在拖动 Codex 窗口边缘、缩放整个窗口，不是旋转模型。

## 可复现的剩余开销

上一轮虽然把连续 resize 绘制限制为 30 Hz，但每次仍调用 Three.js `setDrawingBufferSize`，写入 canvas 的 width 和 height，重新分配并清空 WebGL / MSAA 缓冲区。降低 DPR 没有避免这项工作。

本次在同机 Codex 内置浏览器、隔离 MCP 宿主中，以实际发行 HTML、实际 Python MCP 处理器和复制的工程进行对照。编辑场景为 5 件、2,663,830 面，DPR 2；模型已加载。初始 iframe 1000 × 800，连续改变宽高 4 秒，停止后继续统计 500 ms。未修改用户的真实工程，也未直接操作 Codex 原生窗口。

| 指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| canvas 尺寸写入次数 | 234 | 2 |
| 尺寸 setter 累计主线程耗时 | 314.1 ms | 8.6 ms |
| WebGL draw calls | 1,287 | 11 |
| 宿主尺寸回传 | 0 | 0 |
| 超过 50 ms 的主线程任务 | 0 | 0 |

修复后两次尺寸写入对应最后一帧的 width / height；11 个 draw calls 是完整场景一次绘制，不是 11 帧。另一次首尾尺寸相同的测试为 0 次尺寸写入、11 个 draw calls。

两版隔离宿主 rAF 最大间隔分别约 7.9 / 7.8 ms：本实验验证的是消除插件侧重复绘制和缓冲区分配，不能宣称测得 Codex 原生应用的 FPS 提升或完全解决宿主卡顿。GPU 完成时间未测量。原始记录在本机 `runs/window-resize-20260922/`。

## 修改与取舍

- `studio/web/render-loop.js`：收到 resize 后取消待绘制帧，合并状态变化；连续拖动期间由浏览器合成上一帧，停止 150 ms 后以最终尺寸重建和绘制。正常旋转、滚轮缩放仍按需实时绘制。
- canvas 使用 `object-fit: contain` 保留上一帧比例，拖动中允许临时留边；停止后画布比例与视口相同，恢复完整清晰画面。
- 编辑、打印、任务预览、观察和离线成果共用该调度。窗口持续缩放期间动画画面也暂停，停止后恢复；不改变模型文件、几何精度或最终 DPR。
- `tests/test_render_loop.mjs`：144 Hz 连续尺寸变化期间零绘制、结束后一次绘制；已排队动画/模型变化不能穿透暂停；隐藏、重新显示、销毁和尺寸去重继续验证。

验证：前端 51 项、MCP / 工作区回归 34 项通过；自包含工作台和离线成果构建成功。原生窗口最终手感仍需用户加载新版后确认。
