# 场景内选中、编辑与绑骨：Cubely 接入提案

2026-09-23。状态：用户已确认实施；第一阶段实现见 [场景编辑](../SCENE_EDITING.md)，验证见 [验收记录](VALIDATION_20260923_SCENE.md)。

## 产品行为

以 Codex 项目文件夹管理场景，继续使用 Studio 右侧视口。用户点击人物、家具或机构，
选中对象进入当前任务上下文；可以移动、改材质、编辑模型、检查骨架、绑骨或编辑动作。
AI 使用当前 Codex 的推理能力和本地工具，专业生成 API 可选。

例如：选中湖边人物 →「修好右肩抬手变形」→ 保留原件并生成候选 → 在抬手和行走姿态
检查蒙皮 → 通过后原位替换 → 其他任务看到提交后的新版本。失败时继续显示原版本。

## 实际核对

调查附件 `cubely_lab_20260920.zip`，只解压源码并读取资产清单与 GLB JSON，未执行附件脚本、
调用其中的服务或启动完整游戏。外部素材位置不进入插件源码。

- `public/models/pedestrians/manifest.json` 有 9 个角色；逐个读取原 GLB，均有 1 个 skin
  和 `Continuous_Pedestrian_Safety` 动画，骨骼关节数为 29–52。它们已有骨架，不必全部重绑。
- `public/models/living/manifest.json` 有 44 类设施，均带 liteUrl。其 accepted / trajectorySafe
  是附件原有标签，本轮没有独立验收其视觉效果或运动安全。
- `lib/sim/character-assets.ts` 使用 SkeletonUtils.clone、AnimationMixer、骨骼语义映射，
  已有角色动作、IK 辅助和物理状态处理。载入器硬编码 9 人并依赖指定骨骼语义，不能直接当
  任意角色通用载入器。
- `lib/sim/living-city.ts` 分开保存设施 asset 与 instance；已有轻量模型、距离加载、
  16 个可见 / 22 个驻留的预算。这些是代码配置，不是本轮测得的 FPS。
- `GameEngine.selectObject()` 当前用于导航与交互目标，不等于编辑器的拾取、变换与历史。
  许多实例 ID 来自生成次序，持久化编辑不能无条件依赖这些 ID。
- `scripts/rerig-people.mjs` 是调用 Assembly 绑骨工作流的批处理，不是本地 GPT 绑骨算法。
  脚本存在不证明该端点当前可用，也不关闭 Lux3D 专用 key 缺口。

本轮资产检查输出：`~/test/cubely-scene-feasibility-20260923/asset-inspection.json`。

## 与现有 Studio 衔接

[文件夹工程](../FOLDER_PROJECTS.md) 已有共享工程、对象版本、租约、独立选区/撤销及 worktree 隔离。
[动作编辑](../MOTION_EDITING.md) 已有保留 skin 的导入、骨骼局部旋转、片段裁剪与本地 Blender 路线。

普通静态编辑入口会拒绝 skin、animation 和 morph，不能移除这个保护来伪装场景支持。
人物必须保持完整 rig；拓扑、蒙皮和复杂动作在 Blender 工作副本中处理，再验证整体回填。
现有动作入口也不等于任意角色的可靠自动绑骨或通用 IK 编辑器。

## 建议的数据与交互边界

1. **场景实例和资产版本分开。** 实例保存稳定 ID、父节点、局部变换及资产版本引用；资产保存
   几何、材质、骨架和动作。默认只改选中实例，首次修改共享资产时生成独立版本。
   「更新全部同源实例」必须是显式操作，并检查受影响实例的版本与编辑范围。
2. **编辑状态与运行状态分开。** 场景布局属于工程；NPC 此刻的走动、物理速度、游戏进度属于
   运行预览。进入编辑暂停模拟，退出后恢复；只把明确保存的姿态/变换写入工程。
   修改尺寸或位置需要同步重建相关碰撞/导航数据，不能只移动画面。
3. **使用同一个编辑视口。** 场景总览、对象隔离和骨架/动作检查切换相机与工具面板。
   复用 Cubely 的角色与设施载入逻辑，适配到 Studio 的渲染调度；不要在后台再跑一个完整游戏
   renderer。实时控制正在运行的 Cubely 需要额外 runtime adapter，不能由静态导入自动获得。
4. **选中对象就是 AI 操作范围。** 上下文包含场景/实例/资产 ID、版本、变换、骨架/动作摘要及
   必要的观察图；大网格留在工具侧按需读取。右键对象开任务继续沿用 scope、租约与冲突检查。
5. **验证后提交与原位更新。** 候选生成、验证和当前版本分开；提交后广播受影响对象的新引用。
   保留位置、朝向、比例以及可兼容的动作状态，不重新下载并加载整场景。骨架改变时重新绑定
   并明确重启动作，不能套用旧骨骼索引。旧请求不能覆盖更新版本。

## 第一阶段建议范围

用附件中的一个小场景片段（2 个人物、1 个设施）验证：

- 场景树与视口点选一致，选区进入 AI 上下文；可隔离查看人物及骨架。
- 修改一个实例的变换/材质，不改变同源的另一个实例。
- 使用已有动作播放；在 Blender 修改完整 rig，返回候选并原位替换。
- 用另一个无骨架样本验证「GPT 本地绑骨 → 动态观察 → 保存」，不承诺任意角色一次成功。
- 场景保存重开；另一任务同步看到提交；同对象抢写拒绝；撤销不覆盖别人的修改。
- 错误候选/载入失败保留原画面；连续缩放不重复加载资源。分别记录浏览器测试和原生 Codex
  窗口实测，不能用前者替代后者。

通过后扩到完整 Cubely 场景、场景摆放、人和设施的接触/路径编辑及运行时联动。
第一阶段不把整套驾驶、任务剧情、NPC 行为系统搬入 Studio。

## 已确认的架构选择

建议按以上「实例与资产分层、先做小场景闭环、复用现有视口和协作机制」实施。
用户于本轮以「开干」确认上述第一阶段范围。后续完整城市运行时联动单独推进，旧工程不自动迁移。
