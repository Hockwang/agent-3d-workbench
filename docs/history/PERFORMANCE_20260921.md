# 2026-09-21：打开与缩放工作区的性能修复

后续：用户确认原生窗口缩放仍卡顿，2026-09-22 将拖动期间的 30 Hz 重建改为停止后重建，见 [窗口缩放跟进](WINDOW_RESIZE_20260922.md)。下文为第一轮记录。

用户报告打开插件后缩放 Codex 界面明显卡顿。本轮找到并修复插件侧可复现的四项开销。

## 根因与修改

| 文件 | 问题与修复 |
| --- | --- |
| `studio/app/api.js`、`studio/app/binary.js` | 原 GLB 解码用 `Uint8Array.from(string, callback)` 对整份模型逐字节回调。122 MB 测试资产会造成秒级长任务。改为每段 1 MiB Base64、段间让出事件循环，优先原生解码，兼容旧浏览器的循环解码。字节内容不变。 |
| `studio/app/main.js` | 宿主尺寸事件重复激活工作区；SDK 自动测量 `max-content` 再向宿主回传尺寸。改为区分展示模式变化与单纯尺寸变化；仅对话卡片主动报高度，工作区由宿主决定大小。打印预览也使用分块解码。 |
| `studio/web/workspace.js` | `setActive(true)` 即使已经激活也刷新后台。改为幂等激活。 |
| `studio/web/render-loop.js` | 新增两个视口共用的按需调度：静止时休眠；交互最高 60 fps，连续容器缩放最高 30 fps；相同尺寸不重复分配缓冲区。缩放过程中 DPR 上限 1，停止 150 ms 后恢复上限 2。 |
| `studio/web/editor-viewport.js`、`studio/web/viewport.js` | 接入调度；视角、模型、选区、控件变化唤醒渲染。合并 window resize 与 ResizeObserver 事件；销毁时清理监听器、控件和 GPU 资源。 |
| `studio/web/editor.js` | 相同工程版本、忙碌状态和打印来源不重复重绘界面与选框。以最近一次实际渲染状态为准，确保只读操作或失败后也能恢复按钮。 |
| `studio/web/style.css` | canvas 的 CSS 尺寸由容器决定，避免 drawing buffer 尺寸反向撑大布局。 |
| `studio/app_resources.py`、`README.md` | MCP UI 资源更新为 `studio-v5.html`，使新入口取得新构建。 |
| `tests/test_render_loop.mjs`、`tests/test_binary.mjs` | 补充静止休眠、144 Hz 尺寸事件合并、恢复清晰度、隐藏/销毁、重复尺寸分配、分块让出线程及解码字节一致性测试。 |

模型几何没有减面或替换；临时变化只涉及窗口缩放过程中的画布分辨率。

## 测量方法

- 同机 Apple M5 Pro，Codex IAB 内的隔离 MCP App 宿主，DPR 2。未操作 Codex 原生窗口。
- 基线为已安装的 `0.6.0+codex.20260921120621` 自包含 HTML，修复版使用本仓构建。两版调用相同后端。
- 复制原打印工程到临时目录。打印使用现有每件最多 3 万面预览；编辑使用完整 5 件、2,663,830 面模型，GLB 资产约 122 MiB。
- 每轮持续改变 iframe 宽高约 4 秒，再静止约 4 秒。记录 WebGL draw calls、canvas width/height 写入、MCP 请求、尺寸回传、rAF 间隔与 PerformanceObserver 长任务。
- “启动”轮次重载 iframe 后立即缩放，包含资源接收、解码与首次绘制；模型文件和操作系统磁盘缓存均已预热，不代表首次安装后的磁盘冷启动。
- 原始记录见 `performance-20260921.json`，含单变量验证和中间失败记录。初始化失败的那次已标为无效，未用于结论。

## 实测

| 指标 | 旧版 | 修复后 |
| --- | ---: | ---: |
| 启动并缩放：最大 rAF 间隔 | 1,312.5 ms | 55.5 ms；复测 42.0 ms |
| 启动并缩放：主线程长任务（超过 50 ms） | 4 次，最长 1,296 ms | 两轮均 0 次 |
| 已加载编辑场景：缩放期间 draw calls | 6,490 | 1,276–1,287 |
| 已加载编辑场景：静止阶段 draw calls | 6,138 | 11（最后一帧恢复清晰度） |
| 已加载打印场景：缩放期间 draw calls | 8,246 | 1,652 |
| 已加载打印场景：静止阶段 draw calls | 7,840 | 28（最后两帧） |
| 已加载打印场景：画布尺寸写入 | 2,270 | 234（含最终清晰帧） |
| 已加载编辑场景：状态请求 / 尺寸回传 | 31 / 569 | 3 / 0 |

单独阻止重复激活，空场景状态请求先从 33 次降到 2 次，但仍有高频重绘。
仅修渲染与宿主通知后，启动仍有最高约 1.38 秒停顿；补充分块解码后，秒级停顿消失。这将启动阻塞与窗口缩放开销区分开来。

上述 draw calls 是调用次数，rAF 是宿主心跳，不是 GPU 完成耗时，也不是 Codex 整个应用的 FPS。已加载场景旧版在隔离宿主内也没有长帧，但存在大量冗余工作；实际复现的秒级卡顿发生在打开并加载完整网格时。

## 回归与边界

- 94 项 Python 测试、20 项 Node 测试通过；自包含构建成功。2 项 Bambu 实机测试未执行。
- 实际操作验证：模型旋转、滚轮缩放、新建、检查网格、非法减面参数失败后重试、撤销、选区刷新、收起和重新打开。
- 收起再打开，网格资源读取次数保持 26，没有重新下载已载入的对象。
- 所有写操作仅发生在隔离工程；原打印工程未修改。
- 本轮没有直接操控/测量 Codex 原生窗口拖动；结论限定为插件及同机 MCP 宿主中的可复现性能。原生宿主最终交互需加载新版后复验。
- 完整网格首次加载仍需要传输和分配约 122 MiB 资产，瞬时内存不会降到轻量预览水平；本轮主要消除阻塞和不必要的持续渲染。
